\begin{abstract}
Gateways that block domains must turn names seen by deep packet inspection (DPI) into packet
drops on IP addresses. We ask how long that takes and whether the first connection to a blocked
domain gets through. We built \sys{}, which couples NFStream/nDPI flow inspection with an
eBPF/XDP blocklist, and measured three decision strategies on a Linux testbed, 100 trials each.
Acting when a flow is exported blocked domains a median of \SI{\medExp}{\milli\second} after the
ClientHello (over the \enforcedExp{} of \nExp{} flows it acted on; on a quiet link the rest never
were) and never stopped the first connection. Acting on every packet inside the DPI engine cut the median to \SI{\medEarly}{\milli\second},
a delay we trace to buffered packet capture rather than to classification; across emulated
round-trip times of 5 to \SI{1000}{\milli\second} it stopped only the fraction of first
connections that this delay predicts, \sweepEarlyhundred\% at \SI{100}{\milli\second}. A fast
path that parses only TLS ClientHellos from an unbuffered, BPF-filtered socket blocked domains
\SI{\medFast}{\milli\second} after the ClientHello and stopped every first connection at every
round-trip time. When the server name spans two TCP segments, falling back to the per-packet
path instead of flow export cuts enforcement from about \SI{6}{\second} to half a second. The XDP
hash-map blocklist kept a constant per-packet cost from 1 to \num{10000} entries, while linear
iptables rules lost 98\% of their throughput. We release the system, the testbed and all raw
measurements.
\end{abstract}

\keywords{eBPF, XDP, deep packet inspection, TLS SNI, packet filtering, measurement}

\section{Introduction}

Network operators block domains, but packets carry IP addresses. A campus, enterprise or home
gateway that must stop traffic to \texttt{youtube.com} has to learn which server addresses
currently serve that name, and then drop their packets fast enough for the policy to hold.

Deep packet inspection solves the first half: libraries such as nDPI~\cite{ndpi} read the
server name from the TLS ClientHello's Server Name Indication (SNI)~\cite{rfc6066,rfc8446},
from QUIC~\cite{rfc9000}, DNS or the HTTP \texttt{Host} header. eBPF and the eXpress Data Path
(XDP)~\cite{xdp} solve the second: an XDP program drops packets in the driver, before the kernel
allocates socket buffers, and its blocklist can be changed at run time through BPF maps.

This paper studies what happens \emph{between} the two halves: how long it takes from the
moment a blocked name appears on the wire until the kernel drops that server's packets, and
whether the first connection completes in the meantime. A blocker that lets every first
connection through is weak in practice: a page load, an API call or a software update may need
only one connection.

We built \sys{}, an open-source blocker that pairs DPI with XDP~\cite{dpiguard}, and measured three
decision strategies. Our main finding: the dominant delay is not DPI or the kernel but how
packets reach user space:
\begin{itemize}
  \item Acting when a flow is \emph{exported} waits for the flow's idle timeout, so the first
        connection always completes (median time-to-block \SI{\medExp}{\milli\second} over the
        flows that were enforced); on a quiet link the flow may never be exported.
  \item Acting in a \emph{per-packet} DPI hook is faster, but buffered libpcap capture delivers
        packets in blocks on a timer, adding a uniform 0--\SI{1}{\second} delay (median
        \SI{\medEarly}{\milli\second}). At an emulated \SI{100}{\milli\second} round-trip time
        it stops only \sweepEarlyhundred\% of first connections.
  \item A \emph{fast path}, a filtered \texttt{AF\_PACKET} socket that wakes only for TLS
        ClientHellos, reduces time-to-block to \SI{\medFast}{\milli\second}; the server's
        first reply is dropped and every first connection fails, at every round-trip time we
        tested.
\end{itemize}

\noindent\textbf{Contributions.} (1)~The design and implementation of a DPI-guided XDP domain
blocker with a two-path architecture and a header-free user-space controller that drives BPF
maps through the \texttt{bpf(2)} system call (\S\ref{sec:design}). (2)~A measurement of
time-to-block for three decision strategies that identifies capture buffering as the dominant
delay, and shows how it decides whether the first connection survives across round-trip times
(\S\ref{sec:ttb}, \S\ref{sec:rtt}). (3)~A fallback design for ClientHellos the fast path cannot
read, measured against the original (\S\ref{sec:split}). (4)~A comparison of drop cost and blocklist scaling for XDP hash maps,
nftables sets and iptables rules (\S\ref{sec:cost}). (5)~A policy model that maps domain rules
to IP addresses with exact unblocking and reports collateral blocking (\S\ref{sec:design}).

\section{Background and Related Work}
\label{sec:background}

\textbf{Packet capture.} User-space monitors read packets through libpcap, which descends from
the BSD Packet Filter~\cite{bpf}. On Linux, libpcap uses a memory-mapped \texttt{TPACKET\_V3}
ring that hands \emph{blocks} of packets to user space when a block fills or its timeout
expires, trading latency for throughput. Immediate mode~\cite{pcapimmediate} removes this delay,
but frameworks built on libpcap do not always expose it.

\textbf{DPI and flow export.} nDPI~\cite{ndpi} classifies flows and extracts metadata such as
the TLS server name. NFStream~\cite{nfstream} wraps nDPI in a Python flow-measurement framework
that exports a record when a flow ends (idle or active timeout) and runs user plugins on every
packet.

\textbf{Kernel packet filtering.} XDP~\cite{xdp} runs verified eBPF programs at the earliest
point of the receive path and is used in production for DDoS mitigation~\cite{bertin}. Scholz et
al.~\cite{scholz} analysed the performance of eBPF-based filtering, and bpf-iptables~\cite{bpfiptables}
showed that rule-by-rule iptables matching degrades with the number of rules while eBPF data
structures do not. nftables sets offer hash-based matching inside netfilter, including on the
early \texttt{netdev} ingress hook.

\textbf{Name-based blocking and its limits.} SNI is sent in clear text in TLS 1.2 and
1.3~\cite{rfc6066,rfc8446}, which makes it a common signal for filtering and
censorship~\cite{chai}. Encrypted Client Hello (ECH), standardized in 2026~\cite{ech,svcbech},
encrypts the whole ClientHello, including the SNI, wherever both ends deploy it. Blocking by IP
has collateral effects when domains share addresses, and Hoang et al.~\cite{hoang} show how
widely domains are co-hosted.

\textbf{Why not block at DNS?} The simplest domain blocker is a resolver that refuses or
rewrites queries for listed names, as with DNS Response Policy Zones~\cite{rpz} or home
sinkholes such as Pi-hole. It acts before the first connection exists and costs nothing per
packet, but it governs only clients that use that resolver: encrypted DNS such as
DoH~\cite{doh}, a hard-coded resolver or a cached or literal address bypasses it. Enforcing on
the SNI and server address of the traffic itself does not depend on the client's resolver,
which is why \sys{} pays the cost of turning names into addresses on the data path.

\textbf{Name-to-address policies with eBPF.} The closest prior system is Cilium's DNS-based
policy~\cite{cilium}: a DNS proxy observes which addresses a workload's queries resolve to and
admits only those, enforced in eBPF. It learns names from DNS answers inside a Kubernetes
cluster; \sys{} learns them from TLS on the wire, so it needs no control over the client's
resolver, which brings the time-to-block question we study.

\textbf{Gap.} Prior work evaluates either classification or filtering throughput in isolation.
We measure the end-to-end delay between classification and enforcement, and whether a
DPI-guided blocker stops the \emph{first} connection.

\section{Design}
\label{sec:design}

\sys{} splits the work in two: user space decides \emph{which} addresses to block from the
names it observes, and an XDP program in the kernel drops their packets
(Figure~\ref{fig:arch}).

\textbf{Enforcement.} One XDP program on the monitored interface parses Ethernet, up to two
VLAN tags and the IPv4 or IPv6 header, and looks up both the source and destination address in
a hash map with \num{65536} entries per address family. A hit returns \texttt{XDP\_DROP} and
increments that entry's packet and byte counters; a miss returns \texttt{XDP\_PASS}. Matching
both directions drops a blocked server's replies on an end host and outbound requests on a
gateway. Global counters live in a per-CPU array, so the hot path takes no shared locks.

\textbf{Decision.} Two taps feed the controller. The \emph{fast path} is an \texttt{AF\_PACKET}
socket with a 28-instruction classic-BPF filter that accepts only IPv4 TCP segments to port 443
whose payload begins with a TLS handshake record of type ClientHello; user space therefore
wakes only for connection openings, parses the SNI and reports (name, server IP) at once.
\emph{NFStream with nDPI} inspects all traffic and keeps per-domain statistics. It is also the
fallback for names the fast path cannot read (QUIC, DNS, HTTP, a ClientHello whose server name
falls in a later TCP segment): a plugin that runs on every packet reports a name as soon as nDPI
has reassembled it. Our first version fell back to flow export instead; \S\ref{sec:split}
shows the difference.

\textbf{Policy.} A rule such as \texttt{youtube.com} matches the name and all subdomains; the
most specific rule wins. The controller remembers every observed (domain, IP) pair, so adding a
rule blocks already-seen addresses at once, and removing one unblocks exactly the addresses no
remaining rule needs. When a blocked address also serves an allowed name, the controller
reports it as collateral.

\textbf{Implementation.} \sys{} is about \num{1000} lines of Python plus a 128-line XDP program
compiled ahead of time with clang and loaded with iproute2. The controller manipulates the
pinned maps with five \texttt{bpf(2)} commands issued through \texttt{ctypes}, so it needs no
BCC or kernel headers at run time. A Flask API exposes rules and counters. Twenty-six
automated tests, three of which run XDP and nftables on a veth pair inside a network namespace,
check enforcement end to end.

\section{Methodology}
\label{sec:method}

\textbf{Testbed.} A KVM virtual machine with 4~vCPUs (Intel Xeon, \SI{2.8}{\giga\hertz}),
\SI{15}{\giga\byte} RAM, Linux 6.18 and iptables 1.8.10 (nf\_tables back end). A sender in a
network namespace reaches the host through a veth pair; filters attach to the host-side
interface (XDP in native mode). A TLS~1.3 server in the namespace answers one HTTP request per
connection.

\textbf{Time-to-block (\S\ref{sec:ttb}).} For each configuration we run 100 trials. Trial $i$
connects to its own server address with SNI \texttt{t$i$.blocked.test}, so earlier blocks never
affect later trials. The client records the time just before sending its ClientHello; \sys{}
records when it wrote the IP to the XDP map. Their difference is the \emph{time-to-block}.
Consecutive trials are separated by a random gap of 0.25--\SI{1.25}{\second}, so their start
times cannot phase-lock with periodic timers in the capture path. A first connection counts as
\emph{stopped} if its TLS handshake or HTTP exchange fails within
\SI{2}{\second}. Every trial is paired with a control connection to an allowed name on another
address, which must succeed. We report medians with 95\% percentile-bootstrap confidence
intervals and proportions with 95\% Wilson intervals.

\textbf{Emulated round-trip time (\S\ref{sec:rtt}).} Our kernel lacks the \texttt{netem} queueing
discipline, so the server emulates distance itself: it waits $D$ milliseconds after accepting a
connection before reading the ClientHello and replying. For a blocker next to the client, which
is where \sys{} runs, the server's first reply then arrives $D$ after the ClientHello, as it
would with a round-trip time of $D$. We sweep $D$ from 5 to \SI{1000}{\milli\second}.

\textbf{Split ClientHello (\S\ref{sec:split}).} Large ClientHellos span several TCP segments;
an X25519+ML-KEM-768 hybrid key share alone adds \num{1216} bytes. We emulate this by sending the first 100
bytes of the ClientHello in their own segment, which places the server name in the second.

\textbf{Drop cost and scaling (\S\ref{sec:cost}).} A C sender (\texttt{sendmmsg}, batches of 64
UDP packets, 64-byte frames) floods the host for \SI{5}{\second} while pinned to one vCPU. On a
veth pair the receive path runs on the sending CPU, so the achieved sender rate measures the
whole per-packet path. For drop cost we block the sender's address; for scaling we fill the
blocklist with $N$ random addresses that never match, so every packet takes the full
no-match path. Each configuration runs 5 times; we report the mean and sample standard
deviation.

\section{Results}

\subsection{Time-to-Block}
\label{sec:ttb}

\begin{figure}[t]
  \centering
  \includegraphics[width=\columnwidth]{figures/time_to_block.pdf}
  \Description{Cumulative distribution of time-to-block on a log scale: the fast path is below 3 ms, the plugin spread between about 5 ms and 1 s, and flow expiry between 5 and 7 s.}
  \caption{Time from the client's ClientHello to the kernel block, \nFast{} trials per mode. The
  expiry curve stops at \enforcedExp/\nExp: the remaining flows were never exported.}
  \label{fig:ttb}
\end{figure}

Figure~\ref{fig:ttb} shows the distribution of time-to-block for each mode, with no added
delay.

\textbf{Flow expiry} acts only after the connection has ended and stayed idle for the
\SI{5}{\second} timeout. Every first connection completed (\stoppedExp/\nExp{} stopped), and the
block landed a median of \SI{\medExp}{\milli\second} (95\% CI \numrange{\loExp}{\hiExp}) after
the ClientHello, over the flows that were enforced. NFStream checks for idle flows only when new packets arrive: \enforcedExp{} of
\nExp{} flows were enforced within the observation window, and the rest, from the last trials
before the link went quiet, never were. On a quiet link, export-based enforcement has no upper
bound.

\textbf{The NFStream plugin} sees the server name on the connection's fourth packet, yet the
block landed \SIrange{\minEarly}{\maxEarly}{\milli\second} after the ClientHello (median
\SI{\medEarly}{\milli\second}, 95\% CI \numrange{\loEarly}{\hiEarly}). Almost all of this delay
lies between a packet's capture timestamp and the plugin call, and it is spread evenly over
0--\SI{1}{\second}: the signature of a capture buffer released on a timer. Classification and
the map update take well under a millisecond. With no added delay the server replies first, so
\stoppedEarly/\nEarly{} first connections were stopped.

\textbf{The fast path} removes the buffer: the block landed
\SIrange{\minFast}{\maxFast}{\milli\second} after the ClientHello (median
\SI{\medFast}{\milli\second}, 95\% CI \numrange{\loFast}{\hiFast};
\SI{\medFastDetect}{\milli\second} from frame arrival to map update). The server's first reply
was dropped, so \stoppedFast/\nFast{} first connections failed. All \controlsAll{} control
connections succeeded.

\subsection{Does the First Connection Survive Distance?}
\label{sec:rtt}

\begin{figure}[t]
  \centering
  \includegraphics[width=\columnwidth]{figures/rtt_sweep.pdf}
  \Description{Fraction of first connections stopped versus emulated round-trip time: the fast path stays at 100 percent; the plugin rises from near zero to 100 percent only at 1 s, matching its predicted curve.}
  \caption{Fraction of first connections stopped against the emulated round-trip time
  (\sweepN{} trials per point, 95\% Wilson intervals). The dotted line predicts the plugin's
  curve from its zero-delay time-to-block alone.}
  \label{fig:rtt}
\end{figure}

A block stops the first connection only if it lands before the server's reply, so the answer
depends on the round-trip time (RTT). Figure~\ref{fig:rtt} sweeps the emulated RTT from 5 to
\SI{1000}{\milli\second}. The fast path stopped \sweepFastfive/\sweepN{} first connections at
every RTT, including \SI{5}{\milli\second}. The plugin stopped \sweepEarlyfifty/\sweepN{} at
\SI{50}{\milli\second}, \sweepEarlyhundred/\sweepN{} at \SI{100}{\milli\second},
\sweepEarlyfivehundred/\sweepN{} at \SI{500}{\milli\second} and \sweepEarlythousand/\sweepN{}
only at \SI{1}{\second}. Its curve follows the prediction from Figure~\ref{fig:ttb}, i.e.\ the
fraction of zero-delay trials blocked within the RTT, inside the confidence interval at every
point: the plugin's chance of stopping a first connection is set by the capture buffer's timer,
not by the network. At the RTTs common on the Internet, tens to a few hundred milliseconds, the
plugin lets most first connections through and the fast path lets none through. All
\sweepControls{} control connections succeeded.

veth then processes frames through an extra NAPI step; this overhead is specific to veth.

\section{Discussion}
\label{sec:discussion}

\textbf{Where the time goes.} In a DPI-guided blocker, the kernel and the classifier are fast;
the delay comes from how packets reach the classifier. Export-on-expiry ties enforcement to the
flow's end and to later traffic. A per-packet hook fixes the first problem but inherits the
capture library's buffering. A narrow, unbuffered tap for the one message that names the server
fixes both. Latency-critical decisions in monitoring systems need their own capture path.

\textbf{An operational lesson.} During development, NFStream's meter processes, which ignore
\texttt{SIGTERM}, outlived the controller and kept capturing; while these orphans ran, blocked
traffic intermittently bypassed the XDP program on our veth testbed. The controller now
force-kills its children on exit, and every measurement in this paper was taken with that fix
in place. Capture processes must be supervised as strictly as the filter itself.

\textbf{Limitations.} \emph{Collateral blocking:} enforcement is per address, so an allowed
name sharing a CDN address with a blocked one is blocked too; \sys{} reports but cannot avoid
this~\cite{hoang}. \emph{Hidden names:} ECH is now a standard~\cite{ech,svcbech}; where it is
deployed, the SNI that \sys{} (and nDPI) reads is only an innocuous outer name, and encrypted
DNS hides the query too. Name-based blocking of any kind loses its signal as ECH spreads.
\emph{Large ClientHellos:} this is a common case today, not an edge case. Chrome offers an
X25519+ML-KEM-768 hybrid key share by default~\cite{chromemlkem}, as do other clients, which
pushes the ClientHello past one TCP segment and can place the SNI in the second; middleboxes
that read only the first segment have already failed in deployment~\cite{traefikpq,traefikcve}.
\sys{}'s fast path also parses only the first segment, so for such clients enforcement falls
back to the plugin's sub-second delay (\S\ref{sec:split}). Reassembling the ClientHello in the
fast path is the most important next step. \emph{QUIC:} the fast path handles TCP only; QUIC Initial packets are encrypted with
keys derived from public values, so a QUIC fast path is feasible but not yet built.

\textbf{Threats to validity.} All measurements come from one virtual machine on a veth pair
with sub-millisecond RTT, which hides XDP's main advantage and adds a NAPI step of its own. Round-trip
time is emulated by delaying the server's reply, not the network, so it does not model loss or
queueing. IPv6 was disabled in the kernel, so only IPv4 was measured. Client and controller
timestamps share one clock. Samples are 100 trials per time-to-block configuration and 5 runs
per throughput point.

\section{Conclusion}

A DPI-guided blocker is only as fast as the path that carries packets to its classifier.
Acting on exported flows took a median of \SI{\medExp}{\milli\second} where it acted at all,
and never stopped a first connection;
acting inside the DPI engine took \SI{\medEarly}{\milli\second} because of capture buffering,
and stopped first connections only as often as that delay predicts; a ClientHello fast path
took \SI{\medFast}{\milli\second} and stopped every first connection at every round-trip time,
while the XDP blocklist kept a constant cost from 1 to \num{10000} entries. Future work:
reassembling multi-segment ClientHellos in the fast path, bare-metal runs with native-XDP NICs,
collateral measurements on real CDN-hosted domains, a QUIC fast path, and connection-level
enforcement to avoid collateral blocking. Code, testbed and data are available~\cite{dpiguard}.
